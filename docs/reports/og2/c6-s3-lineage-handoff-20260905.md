# S3 source lineage and recoverable final-CSV handoff

Date: 2026-09-05. This is a controller-only safety correction, qualified on
disposable C5 fixtures. No counting algorithm, canonical key, native
checkpoint format or released binary changed. No real C6 S3 run or complete
N(6) result was produced.

## Read-only readiness finding

The new closed reverse-F5 export has the native layer-5 format and weighted
`T5 = coordinate_orbit_size * F5` expected by the existing S3 engine. Complete
C5 export/load compatibility is already verified. The final native engine
retains wide T6 accumulation, exact division by the orbit size, all 63,199
classes and the G1/G2 bridges. The independent Python semantic verifier
reconstructs canonical representatives, stabilizers, multiplicities, class
uniqueness/order, total mass and both anchor bindings. Python and .NET
BigInteger independently sum the same weighted square. No new defect in
that counting or certificate arithmetic was found.

The old S3 **controller** did have a provenance gap. With
`-ContinueExisting`, the engine loads `<Base>.L5.snap`, but the controller
hashed only the separately supplied `-Layer5` and `-Layer5Backup`. Native
resume checks the local parent's key hash; it does not bind its T5 weights
to the supplied full-file SHA. The progress helper checks C/layer/config
and parent stabilizer intervals, not that external source identity.
Existing complete CSVs could also skip both contractions without a strict
source-bound completion record. Thus an old namespace could be reported
under a different input SHA even though both new path hashes passed.

Adjacent override hazards were equal/overlapping primary and replay bases,
a same-volume or identical input "backup", and unquoted paths passed to
Windows child processes. The old ten-hour-per-attempt default also allowed
two long attempts back-to-back without a shared daily deadline.

These findings are distinct from the present missing prerequisite: a truly
closed C6 F4 export, and therefore a closed numerical C6 F5 export, still
does not exist. Fixing a controller does not supply those mathematical values.

## Corrected controller boundary

`scripts/run_layer_dp_c6_s3_finalize.ps1` now uses
`scripts/layer_s3_lineage.py`. It creates a new immutable per-base
`<Base>.s3-binding.json` before the first actual stage launch. Existing
native artifacts, private leftovers or CSVs without that binding are
refused. There is no automatic legacy migration: use a genuinely new
namespace or obtain a separately reviewed migration procedure.

The binding contains the exact full source SHA, native header/configuration,
source path/length, C and parent layer, role and nonoverlapping peer/base
paths, final CSV path, capacities, chunk geometry, expected target and exact
native algorithm convention. Implementation compatibility includes hashes
of the counting source, its build script, the lineage helper and its imported
header/hash helper, plus compiler executable/version/target identity.

Routine Git HEAD changes and newly stamped MinGW PE binaries do **not**
invalidate an otherwise identical implementation. Git HEAD and the actual
engine SHA remain per-attempt provenance in `command.txt`; they are not the
sole strict resume identity. Thread count, checkpoint interval and bounded
session duration may change; source, algorithm, pinned stage configuration
or chunk geometry may not silently change.

The controller retains Windows deny-write/delete read handles on the local
source, its separate-volume physical copy and existing resume-parent files.
Every resume-parent full SHA must equal the pinned source before use.
Source/copy hashes are checked again at completion. Reparse/symlink paths
and ancestors are rejected in both the controller and helper; primary and
replay namespaces must be distinct and nonoverlapping. A controller-wide
named mutex prevents overlapping S3 controller instances. Child arguments
and retained display commands quote paths containing spaces.

`-PrepareOnly` performs read-only lineage validation but creates no binding,
checkpoint or CSV. As before, it may create diagnostic logs and run the
required verification/resource preflight. Meaningful code/configuration
changes or legacy state are a refusal, not permission to rewrite sidecars.

## Prepared-result transaction

After the original terminal numerical gates and final-snapshot backup, the
controller commits `<Base>.s3-result.json` before moving the private attempt
CSV to its stable name. This immutable receipt pins the binding SHA, source,
role, private/final CSV paths and SHA, final snapshot SHA and command-record
SHA. It is physically backed up, as is the binding.

The receipt is written to an exclusive private file, flushed and committed
without replacement. Publication is then one nonreplacing rename. An
interruption after receipt commit and before that rename can recover only
the exact already-pinned tuple. It cannot adopt another CSV, different
weights, another snapshot, an escaped path or a different source/config.
An already published CSV is rehashed against the same receipt before reuse.

Missing result receipts, inconsistent private/final copies, changed command
records or damaged artifacts fail closed. No incomplete accumulator is
promoted. These JSON files are controller sidecars; the native checkpoint
format and numerical meaning are unchanged. The final summary records both
binding and result-receipt hashes in addition to the original certificate
and external-copy evidence.

## Daily availability and remaining operational prerequisites

The defaults are now `-SessionMaxHours 7.5`, `-ReserveMinutes 15` and
`-MaxHoursPerAttempt 3.5`. `SessionMaxHours` is restricted to at most eight
hours. One common operation deadline covers both numerical attempts,
resource waiting and auxiliary gate/build/verifier children. Auxiliary
children are polled and their process trees are stopped at that deadline;
there is no unbounded auxiliary `WaitForExit`. Hashing also checks the
session deadline between blocks.

This is **not an absolute whole-process wall-clock guarantee**: synchronous
filesystem reads, physical copies and OS calls cannot universally be
interrupted by an in-process check. The operation cutoff leaves the explicit
reserve for backup and handoff work. Use an outer watchdog and an availability
window with headroom; do not assign the complete eight hours to a child or
assume an arbitrarily slow storage device obeys the in-process deadline.
Stopping the controller or losing power cannot guarantee its final cleanup.

Before real S3 use, the closed F4/F5 export receipts and separate physical
copies must exist and be recorded; the source tree must be clean/committed;
the current complete repository gate and S3 preparation must pass; and the
owner must authorize the actual bounded finalization. Primary and replay
remain separate executions of the same counting engine, not two independent
factorization algorithms. Semantic verification and the two integer sums
are separately implemented but do not independently recalculate every F6.
